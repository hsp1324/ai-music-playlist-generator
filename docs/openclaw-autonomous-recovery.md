# OpenClaw autonomous recovery for music production

Use this runbook when production, a scheduled run, or Slack reporting fails. Diagnose the current failure from evidence, make a bounded safe repair, verify it, and continue eligible work in the same pass. Record the failure and repair in the run receipt. A process being alive, a job being enabled, or an API accepting a request is not proof that a song or playlist was completed.

## First: identify the failing layer

1. Check the relevant job and recent run history with `openclaw cron list --all` and `openclaw cron runs JOB_ID --limit 10`. Inspect timestamps, actual error, running state, auto-disable reason, and any earlier failed attempt that is still unresolved. Inspect Gateway status and recent logs as needed. Preserve the configured model, credentials, provider, delivery and schedule.
2. Check the deployed app's current status, release, and shared lock before touching production. A live lock, active Suno generation, login or human verification is a shared blocker: never start a second browser operation, steal the lock, bypass a challenge, or restart away an in-flight submission.
3. Distinguish an OpenClaw dispatch error from an unavailable model, failed provider request, account/quota problem, or a release-specific hold. If the error occurs before a provider call, do not call the model name or reasoning level the cause without evidence. Never print tokens or credentials in logs or reports.

## Gateway and model failures

- For `prepared reply dispatch runtime owner was not published` or a similar pre-dispatch error, inspect Gateway logs, agent preparation and active jobs. If a restart is safe, have an independent supervisor restart the user Gateway once, wait for both readiness and agent database preparation, then run a fresh isolated, no-delivery text test using the configured model and thinking level. Do not restart the Gateway from the only running agent turn if doing so kills the repair, and do not restart during an active generation or lock. If no independent supervisor can run, preserve the evidence and report the actual blocker. A restart is recovery, not proof of the underlying cause.
- For a suspected model or reasoning setting, test the configured model with a minimal fresh isolated session and no external delivery; check the requested and effective model and thinking level. If needed compare supported thinking levels and a previously working model with temporary per-test overrides. Keep the user's chosen default unless the user authorizes a change; never infer model availability from the Gateway's listener alone. Stop retries for authentication, quota or provider outages and respect retry windows.
- Verify that the original job remains configured and can start after repair. If it was auto-disabled by consecutive failures, re-enable the same job only after the underlying blocker has been repaired or safely isolated, the lock and in-flight work have been checked, and no later human edit or manual pause indicates a deliberate stop. Do not create a replacement job or change its schedule. Make at most one bounded recovery attempt per failure episode; record the outcome and avoid repeated auto-enable/failure loops. An existing model-free watchdog may perform its own once-daily retry; do not duplicate or assume it diagnoses the cause. Confirm an actual subsequent run in history.

## Uncertain Suno generation

- Before Create, record the release, workspace, title, prompt/lyrics identity, submission time and visible standard-v6 settings. After submission, record original source IDs separately from derived Studio exports, local files and app track IDs. Never claim creation or download without corresponding proof.
- If a submitted Create's result is unknown, retain its tab and receipts. Do a bounded check of the same current workspace and existing current-batch evidence. An empty search, lost tab, timeout, or spinner does not prove that the provider failed. Do not resubmit the same title, prompt, lyrics, or equivalent request, and do not invent source IDs.
- Record the specific unresolved request and release as quarantined. Do not repeat a broad historical Library inventory or recheck the same unchanged evidence on every pass. Once there is no active provider generation or verification gate and the shared lock is held, continue with a genuinely independent eligible release and distinct original material; never create a replacement for the quarantined release. Follow existing v6 provenance, channel, duration, upload and server-owned scheduling rules. If the shared provider/account/browser itself is blocked, defer all affected generation, but continue unrelated safe work where possible.
- Revisit the quarantined request only when new relevant evidence is available or the human asks. If source IDs later appear, reconcile them with the saved release and record the outcome before acquisition. Do not overwrite or delete existing assets, completed work or prior receipts.

## Garbled Slack reports

Compare the saved assistant transcript with the final Slack message and, if available, the temporary preview. A normal final message with a garbled preview suggests a display/streaming problem; a garbled saved transcript suggests a generation problem. Do not claim a cause without matching evidence. Run a small isolated Korean response test without sending a message to Slack.

If previews are corrupted but the final text is sound, disable Slack live previews with `openclaw config set channels.slack.streaming.mode off`, after a private configuration backup. Verify configuration reload and a fresh agent response; do not assume this proves end-to-end Slack delivery. Preserve channel authorization, destinations and bot filters. Report the change and, if a final message itself is corrupted or the issue recurs, capture the relevant run and delivery evidence and escalate the unresolved cause instead of repeatedly changing models or sending duplicate messages.

## Completion and reporting

Release only the lock owned by this run and record the actual outcome: verified original IDs, complete files, accepted tracks, queued jobs, and remaining blockers. Distinguish `enabled`, `started`, `succeeded`, and real production. If independent work was completed while one request remained quarantined, report both facts; do not report the whole system repaired solely because a job was enabled. Escalate only the specific dependency that needs human login, verification, credentials, provider recovery, or unavailable supervision.
